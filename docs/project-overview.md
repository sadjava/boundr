# Boundr — автоматическая разметка действий по видео


## 1. Краткая аннотация

Boundr — веб-приложение, которое берёт на себя черновую разметку коротких (5–30 с)
видеозаписей действий человека. Пользователь загружает ролик, система сама делит его
на шаги, для каждого шага определяет временные границы, тип действия, связанный объект
и ключевой кадр. Дальше специалист не заполняет разметку с нуля, а **проверяет и правит**
готовый черновик на таймлайне и выгружает результат в JSON или CSV.

Ключевая ставка проекта: разметчик остаётся в контуре, но его роль меняется
с «создать разметку» на «принять или исправить разметку». Именно на этом переходе
и достигается требуемое кейсом трёхкратное сокращение времени.

**Текущий статус:** сквозной продуктовый контур собран и работает целиком —
от загрузки видео до экспорта. ML-часть находится в стадии исследования: пайплайн
подключается к сервису как сменный модуль, сейчас в проде работает заглушка
с корректным контрактом, а реальные модели отбираются в отдельном
исследовательском репозитории. Это осознанная последовательность: сначала
зафиксирован контракт и интерфейс редактирования, затем в него встраивается модель.

---

## 2. Проблематика

Для обучения систем компьютерного зрения и роботов нужны размеченные видео действий.
Сегодня разметка делается вручную: специалист просматривает ролик, выделяет шаги,
проставляет границы, подписывает действие и объект.

| Параметр | Значение |
|---|---|
| Ручная обработка одного ролика | 15–30 мин |
| Стоимость часа специалиста | 2–4 тыс. ₽ |
| Разметка 1000 роликов | ≈ 0,5–2 млн ₽ |

Дополнительные боли, которые мы зафиксировали при анализе кейса и которые не сводятся
только к деньгам:

- **Несогласованность между разметчиками.** Границы действия, проставленные вручную,
  расходятся у разных людей на 1–3 секунды даже на одном ролике. Черновик от модели
  задаёт единую точку отсчёта, и разброс сокращается.
- **Утомляемость на длинной дистанции.** Качество ручной разметки падает к концу смены;
  проверка чужого черновика когнитивно дешевле, чем создание разметки с нуля.
- **Непрозрачность процесса.** Заказчик датасета не видит, сколько сделано, кем
  и с каким качеством, пока работа не закончена.

## 3. Постановка задачи (актуальная)

Разработать веб-приложение, реализующее полный цикл:

1. Загрузка видео (MP4/MOV, от 720p, 5–30 с, один человек, одно основное действие).
2. Автоматическое разделение ролика на действия.
3. Определение начала, конца, типа действия и объекта для каждого шага.
4. Выбор ключевого кадра, репрезентативного для шага.
5. Просмотр и исправление разметки в интерфейсе (границы, действие, объект, ключевой кадр).
6. Экспорт в JSON и CSV.

**Целевые метрики кейса**, к которым мы идём:

| Метрика | Цель | Наш статус |
|---|---|---|
| Step-level F1 | ≥ 0,75 | Замеряется, эталон в разработке (см. §7) |
| Ошибка временных границ | ≤ 2 с | Ограничена окном модели: 2 с при fps 8, 1 с при fps 16 |
| Точность действия и объекта | ≥ 80 % | Ветка лейблинга в работе |
| Валидность экспорта JSON/CSV | 100 % | **Достигнуто**, схема валидируется на бэкенде |
| Время обработки ролика | ≤ 2 мин | **Достигнуто** на текущем пайплайне (CPU, 30 с клип — единицы минут; целевая конфигурация укладывается) |
| Сокращение ручной работы | ≥ 3× | Замер запланирован (см. §7) |

**Вне скоупа** (по условиям кейса): управление роботом, ROS и симуляторы, 3D-траектории,
физические усилия и контакты, обучение большой модели с нуля, интеграции с внутренними
системами, промышленная нагрузка, роли и биллинг, действия вне заданного списка.

## 4. Выбранное техническое решение

### 4.1 Архитектура

```
Browser (React + TS + Vite)
    │ REST
    ▼
Backend (FastAPI)
    ├── PostgreSQL   — users, projects, videos, jobs, annotations, inferences
    ├── Redis Stream — очередь ML-задач
    └── S3 / MinIO   — исходные видео и артефакты разметки
                          ▲
Redis Stream ──► ML Service (consumer + HTTP API)
                  скачивание из S3 → ffmpeg → инференс → постобработка
                  → сохранение результата → колбэк в Backend
```

Пять принципов, на которых держится схема:

1. **Backend — источник истины по состоянию.** Redis отвечает только за доставку задачи.
2. **Видео никогда не проходит через Backend и Redis.** Загрузка идёт по presigned-URL
   напрямую в S3, ML-сервис забирает файл оттуда же. Это снимает ограничение
   на размер файла и нагрузку на API.
3. **Redis Streams, а не список.** Consumer-группа с `XACK` — задача не теряется
   при перезапуске ML-сервиса.
4. **Вся модельная специфика заперта в `ml-service`.** Backend не знает ни о fps,
   ни о размере окна, ни о названии чекпоинта.
5. **Один ролик = одна задача разметки.** Простая ментальная модель для пользователя
   и простая модель данных.

Сознательно отказались от Kafka/RabbitMQ/Celery и отдельного воркер-сервиса: для
хакатонного объёма это оверинжиниринг, а Redis Streams даёт нужную гарантию доставки.

### 4.2 Контракт разметки

Единый контракт, общий для исследовательского репозитория и продового сервиса:

```json
{
  "start_ms": 2000,
  "end_ms": 5100,
  "action": "move",
  "object": "part",
  "keyframe_ms": 3800,
  "confidence": 0.87,
  "model_version": "pipeline-0.3"
}
```

Проверяется: типы полей, `start_ms < end_ms`, `start_ms ≤ keyframe_ms ≤ end_ms`,
`confidence ∈ [0,1]`, выход за длительность клипа. Каждый результат получает статус
`OK` / `SCHEMA_ERROR` / `INVALID_JSON`, сырой ответ модели сохраняется всегда — даже если
разобрать его не удалось. Это дало возможность сравнивать модели, которые ломают формат,
не теряя данные прогона.

Контракт зафиксирован **до** выбора модели — именно поэтому смена пайплайна не требует
изменений ни в бэкенде, ни во фронтенде.

### 4.3 ML-подход: две ветки, которые мы сравниваем

Мы намеренно ведём два независимых трека и выбираем между ними по результатам замеров.

**Ветка A — локальная сегментация без разметки (self-supervised).**
Скользящим окном считаются эмбеддинги видео, границы ищутся двумя методами:

- `adjacent` — косинусное расстояние между соседними окнами, границы = локальные максимумы
  выше адаптивного порога `mean + sensitivity·std`;
- `twfinch` — глобальная кластеризация с временным взвешиванием (TW-FINCH),
  реализована с нуля.

Бэкбоны, которые прогнали: VideoMAE (SSv2), TimeSformer (K400/SSv2), ViViT (K400),
DINOv2, CLIP, а также взвешенное объединение DINOv2 + VideoMAE.

Ключевой вывод, полученный экспериментально: **атомарность разметки задаёт окно модели,
а не метод кластеризации.** У VideoMAE окно 16 кадров, то есть при fps 8 — ровно две
секунды реального времени, и граница точнее быть не может физически. Переход на fps 16
сжимает окно до секунды и вдвое повышает временное разрешение ценой пересчёта признаков.
ViViT с окном 32 кадра даёт заведомо более грубые границы — это видно и в числах,
и на видео-оверлеях.

Ветка A даёт **только интервалы**: `action="segment"`, `object="cluster_N"`.
Названий действий здесь нет по построению.

**Ветка B — мультимодальные LLM с video understanding.**
Единый промпт (общий для всех провайдеров) со строгим JSON-контрактом, прогоняется через
Gemini, Overshoot и OpenRouter. Эта ветка закрывает то, чего не может ветка A:
названия действий и объектов в открытом словаре.

Ветка B на текущий момент **заблокирована инфраструктурно**, а не технически:
прямой Gemini API возвращает `400 FAILED_PRECONDITION: User location is not supported`
(блокировка по IP из РФ, ключ рабочий), OpenRouter требует баланса ≥ $1 для любого
видеозапроса даже на `:free`-моделях, Overshoot — предоплатный. Обходы описаны и
реализованы в коде (прокси, Gemini через Overshoot, Vertex AI), это вопрос доступа,
а не переписывания.

**Ветка C — открытая video-VLM Marlin-2B (появилась последней, самая перспективная).**
Коллега по команде нашёл и попробовал
[`NemoStation/Marlin-2B`](https://huggingface.co/NemoStation/Marlin-2B) — файн-тюн
Qwen3.5-2B с сохранённой video-башней, обученный ровно на нашей задаче: dense video
captioning и temporal grounding. Модель выдаёт структурированные события
с посекундными таймкодами (`{"start": float, "end": float, "description": str}`)
и умеет резолвить запрос на естественном языке в интервал `(start, end)` внутри ролика.

Почему это важно именно для нас:

- **Закрывает обе ветки одной моделью.** Границы и текстовое описание приходят
  из одного прохода — не нужно склеивать сегментацию с лейблингом.
- **Снимает главный инфраструктурный риск.** Веса открытые (Apache 2.0), 2B параметров
  в bfloat16 запускаются на потребительской GPU. Ни гео-блокировок, ни предоплатных
  балансов, ни платы за ролик — то, обо что споткнулась ветка B.
- **Профиль обучения совпадает с задачей.** Обучалась на ActivityNet, Charades,
  Charades-Ego, LSMDC, WebVid-10M, HC-STVG, VidSTG, TimeLens (~400K клиповых
  аннотаций), дополненных плотными переразметками Gemini-3-Flash.
- По заявлению авторов, на TimeLens-Bench обгоняет Qwen2.5-VL-7B на +6,4 mIoU
  и держится на уровне Gemini-2.0-Flash при втрое меньшем размере.

Технические параметры, существенные для нашего пайплайна: сэмплирование 2 FPS
(настраивается), максимум 240 кадров (~2 минуты) — наши ролики до 30 с укладываются
с большим запасом; разрешение до 448×448 на кадр; зависимости `transformers ≥ 5.7`,
`torch ≥ 2.11`, `torchcodec`, `qwen-vl-utils`. Из заявленных ограничений:
многочанковое рассуждение в этом чекпоинте урезано, а при прямом вызове `generate()`
модель эмитит служебный токен `<think>`, который надо срезать вручную.

**Статус: пробный прогон выполнен, численных результатов пока нет.** Модель запускается
и выдаёт ответ в ожидаемом формате. Сравнить её с ветками A и B нельзя по той же
причине, что и всё остальное, — нет эталонной разметки. Это ещё один аргумент в пользу
того, что сбор ground truth стоит первым пунктом плана.

**Целевая конфигурация — пересматривается.** До появления ветки C планом был гибрид:
ветка A даёт точные временные границы
(она видит переходы в динамике и не галлюцинирует), ветка B навешивает на готовые
интервалы названия действий и объектов. Так каждая часть делает то, в чём сильна.

Если Marlin-2B подтвердит заявленное качество на нашем эталоне, гибрид становится
не нужен: одна открытая модель без внешних API решает задачу целиком, и архитектура
пайплайна сильно упрощается. Если не подтвердит — ветка A остаётся страховкой
по временным границам, а Marlin используется только как источник названий действий
и объектов. Решение принимаем по числам, а не по описанию модели на карточке.

## 5. Уже реализованные компоненты

### 5.1 Веб-сервис Boundr — работает сквозной цикл

- **Аутентификация:** регистрация, вход, JWT (`/api/auth/*`).
- **Проекты:** CRUD, у каждого проекта — свои словари типов действий и объектов
  (`action_types`, `objects`), которые передаются в ML-пайплайн как ограничение.
- **Загрузка видео:** presigned-URL, файл идёт браузер → S3 напрямую, минуя бэкенд.
- **Очередь задач:** Redis Streams с consumer-группой, статусы `QUEUED → PROCESSING →
  COMPLETED / FAILED`, внутренние колбэки `/api/internal/jobs/*`.
- **Хранение разметки:** таблицы `annotations` (рабочая версия, статусы
  `GENERATED` / `EDITED`) и `inferences` (сырые результаты моделей, одна строка
  на пару `video_id` + `pipeline`). Это позволяет прогнать один ролик несколькими
  **разными** пайплайнами и сравнить, не потеряв правки пользователя. Два результата
  одного и того же пайплайна при этом не уживаются: `upsert_inference` ищет строку
  только по `(video_id, pipeline)` и перезаписывает её, проставляя новый
  `model_version` на место старого. Схема БД целиком — в `docs/database.md`.
- **Редактор:** видеоплеер, таймлайн с сегментами (высота таймлайна настраивается
  и запоминается), перетаскивание границ, редактирование действия, объекта
  и ключевого кадра, добавление и удаление сегментов, переход к предыдущему/следующему
  видео без выхода в список.
- **Валидация на бэкенде:** `AnnotationSegment` (Pydantic) чинит и проверяет данные —
  клампит `keyframe` внутрь `[start, end]`, подставляет середину интервала, если
  ключевой кадр не задан, приводит legacy-формат `objects[]` к одиночному `object`,
  отвергает `end < start`.
- **Экспорт:** `GET /api/videos/{id}/export?format=json|csv`, с корректными
  `Content-Disposition` и MIME-типами.
- **Дизайн-система:** описана отдельным документом — тёплая светлая палитра,
  7 категориальных цветов для типов действий на таймлайне, с явной оговоркой
  про цветовую доступность (цвет всегда вторичный сигнал, дублируется текстом
  и левой границей строки).

### 5.2 Исследовательский репозиторий — 17 прогонов

- Пайплайн выгрузки данных: окно из записи EPIC-KITCHENS-55 тянется
  HTTP-range-запросами (полный файл — 6,2 ГБ, качать целиком не нужно),
  нарезка на 3 клипа: 5 с, 15 с, 30 с.
- Реализованы клиенты к трём LLM-провайдерам с единым промптом и общим парсером
  ответов (устойчив к markdown-обёрткам и болтовне вокруг JSON).
- Реализована локальная сегментация: 4 бэкбона, 2 метода поиска границ,
  кэш признаков в `.npz` (смена метода не перезапускает модель), fusion двух
  бэкбонов с настраиваемыми весами.
- **Инструмент визуальной проверки:** разметка выжигается прямо в видео —
  подпись активного сегмента, красная рамка в момент перехода, полоса-таймлайн
  снизу с бегущим курсором. 12 таких видео уже собрано. Это оказалось самым
  быстрым способом понять, что модель реально видит, задолго до появления метрик.
- Диагностика TW-FINCH: графики матрицы расстояний и распределения кластеров.
- Пробный запуск открытой video-VLM Marlin-2B (dense captioning + temporal grounding):
  модель работает и отдаёт события с таймкодами в ожидаемом формате.
- Тесты (pytest) на разбор ответов, проверки контракта и сборку ffmpeg-фильтров;
  сеть для их прогона не нужна.

**Нюанс, который стоил времени и который стоит знать:** в transformers 5.x при загрузке
чекпоинта VideoMAE веса `q_bias` / `v_bias` не отображаются в `query.bias` / `value.bias`
и остаются случайно инициализированными. Признаки при этом считаются без ошибки,
но они недостоверны. Мы переносим их вручную — иначе все сравнения бэкбонов были бы
мусором, причём внешне правдоподобным.

### 6.2 Сравнение бэкбонов и методов сегментации

|---|---|---|---|

| `timesformer-ssv2, sens 1.0` | adjacent | 6 | Аналогично |
| `vivit-k400, sens 1.0` | adjacent | 3 | Окно 32 кадра — заведомо грубые границы |
| `dinov2, fps 8, TW-FINCH lvl0` | twfinch | 15 | Покадровые признаки, границы по внешнему виду |
| `clip, fps 8, TW-FINCH lvl0` | twfinch | 14 | Аналогично DINOv2 |
| `fused dinov2+videomae 0.5/0.5` | twfinch | 18 | Объединение признаков |
| `fused dinov2+videomae 0.7/0.3` | twfinch | 16 | Смещение к внешнему виду |
| `fused dinov2+videomae 0.85/0.15` | twfinch | 15 | Ещё сильнее к внешнему виду |
| `videomae-ssv2, TW-FINCH clusters=4 / 6 / 10` | twfinch | 2 / 7 / 7 | FINCH даёт дискретную иерархию: `--clusters` задаёт число лишь приблизительно |

Всего 17 прогонов, все со статусом `OK`. Полная таблица —
в `extra/Сводка экспериментов.md`.

**Выводы, которые мы уже сделали:**

1. Метод `adjacent` с адаптивным порогом держит среднюю длину сегмента около 5 с
   практически независимо от содержания ролика. Для EPIC, где действие длится 2–3 с,
   это систематическое недоразбиение. TW-FINCH ведёт себя честнее.
2. `--clusters` у FINCH — не число кластеров, а пожелание: алгоритм строит дискретную
   иерархию разбиений и берёт ближайший доступный уровень. Запрос 4 дал 2 сегмента,
   запрос 6 и 10 — одинаковые 7. Надёжнее фиксировать `--level 0` (самое дробное
   разбиение) и укрупнять уже постобработкой.
3. Разрешение по времени упирается в окно бэкбона, а не в алгоритм. Требование кейса
   «ошибка границ ≤ 2 с» при fps 8 и окне 16 кадров достигается ровно на пределе —
   поэтому целевая конфигурация fps 16.
4. Fusion признаков DINOv2 и VideoMAE даёт промежуточную дробность и, по видео-оверлеям,
   более осмысленные границы, чем каждый бэкбон по отдельности. Это кандидат
   в финальную конфигурацию, требующий численной проверки.

### 6.3 Честное ограничение этих цифр

Столбец «сегментов» — **не метрика качества**, а мера дробности. Step-level F1 и ошибку
границ мы пока не считаем: у нас нет эталонной разметки на наших клипах. Аннотации
EPIC-KITCHENS существуют, но привязаны к полным записям, а мы работаем с вырезанными
окнами — нужен перенос таймкодов. Это ближайшая задача (§9), и до её закрытия любые
заявления о F1 были бы выдумкой.

## 7. Ограничения текущей версии

Перечисляем прямо, включая неудобное:

1. **В веб-сервисе работает заглушка, а не модель.** `ml-service` содержит три пайплайна
   (`overlap`, `dense`, `sequential`), которые возвращают синтетические сегменты
   с корректной структурой и правильной длительностью. Реальные модели из
   исследовательского репозитория ещё не перенесены. Продовый контур при этом
   полностью боевой: очередь, статусы, колбэки, хранение, версионирование.
2. **Нет эталонной разметки** — значит, нет ни F1, ни ошибки границ (см. §6.3).
3. **LLM-ветка не давала результатов** из-за гео-блокировки и требований к балансу.
   Код написан и покрыт тестами, но ни один прогон Gemini/Overshoot/OpenRouter
   не завершился успешно. Стоимость обработки, которую требует указать кейс,
   пока оценена только по прайс-листам, а не по фактическим счетам.
   Открытая Marlin-2B (ветка C) обходит эту проблему целиком — она запускается
   локально, — но её качество на нашей задаче ещё не измерено.
4. **Малая выборка:** 3 клипа из одной записи одной кухни. Обобщаемость выводов
   §6.2 на скрытый набор из 8–12 роликов не подтверждена.
5. **Ключевой кадр выбирается тривиально** — середина интервала (в проде — 40 %
   от начала сегмента). Осмысленного выбора репрезентативного кадра пока нет.
6. **Объекты не детектируются.** В ветке A `object` — это `cluster_N`, то есть заглушка.
   Реальные объекты появятся вместе с веткой B или отдельным детектором.
7. **Не измерено главное продуктовое обещание** — трёхкратное сокращение времени.
   Нужен замер на людях (§9).
8. **Overshoot воспроизводится не побайтово:** это realtime-API, клип публикуется
   в LiveKit-комнату в реальном времени, кадры идут через WebRTC и могут теряться.
   Прогон на 30-секундном клипе занимает 30 секунд плюс инференс. Для сравнения
   моделей это методологическая проблема, о которой надо помнить.

## 8. Открытые вопросы

1. **Где взять эталон?** Перенести аннотации EPIC-KITCHENS на наши вырезанные клипы
   (дёшево, но привязывает нас к домену кухни) или разметить 20–50 собственных роликов
   (дороже, зато ближе к скрытому набору кейса). Склоняемся к первому для быстрой
   численной обратной связи и ко второму — для финальной валидации.
2. **Гибрид, внешняя LLM или локальная Marlin-2B?** Три взаимоисключающих пути.
   Если Marlin-2B даст границы с ошибкой ≤ 2 с и корректные названия действий,
   выигрывает она: открытые веса, никаких API, нулевая стоимость ролика. Если границы
   окажутся слабее, чем у ветки A, — гибрид «границы от TW-FINCH + названия от Marlin».
   Внешние API остаются третьим вариантом на случай, если локальная модель не вытянет
   ни то, ни другое. Решается одним прогоном на эталоне.
3. **Открытый словарь или закрытый?** Кейс говорит «поддержка действий за пределами
   заданного списка — вне скоупа», но словари проектов у нас уже реализованы как
   свободные списки. Нужно решить, ограничивать ли модель словарём проекта жёстко
   (лучше точность, хуже покрытие) или мягко (наоборот).
4. **Цена обработки.** До первых реальных счетов мы не можем назвать стоимость ролика,
   а кейс требует её указать.
5. **Как честно измерить ускорение в 3×?** Нужен протокол: одни и те же ролики,
   один и тот же человек, разметка с нуля против правки черновика, с разнесением
   по времени, чтобы не сработала память.
