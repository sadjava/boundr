## 1. Цели и предпосылки

### 1.1. Зачем идём в разработку продукта

**Бизнес-цель.** Сократить стоимость подготовки видеодатасетов действий человека.
Сейчас разметка одного 30-секундного ролика занимает 15–30 минут ручной работы при
ставке 2–4 тыс. ₽/час, то есть 1000 роликов стоят 0,5–2 млн ₽.

**Почему ML.** Механическая часть работы — найти границы шагов и подписать очевидное
действие — составляет по нашей декомпозиции ~85 % времени (`product/01`). Она
автоматизируема современными video-VLM; неавтоматизируема только приёмка результата
человеком.

**Ожидаемое улучшение.** Роль разметчика меняется с «создать разметку» на «принять или
исправить черновик». Целевое сокращение времени на ролик — не менее чем в 3 раза.

**Критерии успеха итерации:** `product/04`, уровни 1–3.

### 1.2. Бизнес-требования и ограничения

Требования заданы кейсом хакатона (заказчик — постановщик кейса).

| # | Требование | Значение |
|---|---|---|
| BR1 | Автоматическая разметка ролика на действия с границами, типом действия, объектом и ключевым кадром | Обязательно |
| BR2 | Ручная правка результата в интерфейсе | Обязательно |
| BR3 | Экспорт JSON и CSV | Валидность 100 % |
| BR4 | Step-level F1 | ≥ 0,75 |
| BR5 | Точность действия и объекта | ≥ 80 % |
| BR6 | Ошибка временных границ | ≤ 2 с |
| BR7 | Время обработки ролика | ≤ 2 мин |
| BR8 | Сокращение ручной работы | ≥ 3× |
| BR9 | Запуск одной командой, инструкция, 3–5 примеров | Обязательно |

**Приоритет требований задан заказчиком: BR5 (классификация действий) важнее BR6
(точность границ).** Датасет с верными названиями и границами, сдвинутыми на доли
секунды, пригоден для обучения; датасет с идеальными границами и перепутанными
действиями — нет. BR6 трактуется как обязательный порог, но не как цель оптимизации
(обоснование — `product/02`, гипотеза H2).

**Ограничения на вход:** MP4/MOV, ≥720p, 5–30 с, один человек в кадре, одно основное
действие, без монтажных склеек.

**Использование в бизнес-процессе.** Разметчик открывает видео, получает готовый
черновик, правит и экспортирует. Модель не принимает решений самостоятельно: **человек
в контуре обязателен**, это требование кейса и осознанное решение — цена ошибки
в обучающем датасете слишком высока.

**Критерий успешного пилота:** `product/04`, «Протокол замера ускорения».

### 1.3. Скоуп проекта

Закрываем: BR1–BR3, BR7, BR9 — реализовано; BR4–BR6, BR8 — реализовано технически,
не измерено численно (нет эталона).

Не закрываем осознанно: роли и права, биллинг, промышленная нагрузка, длинные и
монтированные видео, несколько людей в кадре, дообучение на правках пользователя,
интеграции с внутренними системами. Полный список и обоснование — `product/03`.

**Качество кода и воспроизводимость.** Весь стек поднимается одной командой
`docker compose up -d`. Контракт разметки един для исследовательского репозитория
и продового сервиса. Результаты инференса хранятся построчно по пайплайнам
(таблица `inferences`), сырой ответ модели сохраняется всегда — прогон
воспроизводим и разбираем даже при сломанном формате ответа.

**Технический долг, принятый сознательно:** нет автотестов уровня сервиса (только
самопроверки модулей и pytest в `ml-service/tests/`); ключ видео захардкожен как
`original.mp4`; `annotation.json` не различает пайплайны в ключе S3; повторный
прогон пайплайна затирает правки пользователя. Перечень ведётся в `AGENTS.md`,
раздел Gotchas.

### 1.4. Предпосылки решения

| Предпосылка | Обоснование |
|---|---|
| Строим свой продукт, а не плагин к CVAT / Label Studio / Supervisely | Ни один из них не даёт автоаннотацию действий; они дают редактор и пустой слот под модель. Разбор — `product/06` |
| Не обучаем модель с нуля | Прямо вне скоупа кейса; готовые video-VLM решают задачу за один проход |
| Гранулярность — атомарный шаг действия | Соответствует формату целевого датасета: «шаг» в терминах кейса |
| Единица работы — один ролик | Ролики короткие (5–30 с), задача не требует стриминга и разбиения |
| Держим две ML-ветки (внешний API и открытые веса) | Они ломаются по несвязанным причинам: гео-блок и баланс против требований к GPU. Плюс это развилка для заказчика по конфиденциальности (§4.5) |

## 2. Методология

### 2.1. Постановка задачи

Технически это **temporal action segmentation + dense video captioning**: разбить
ролик на непересекающиеся интервалы и для каждого выдать текстовое действие, объект
и ключевой кадр. В терминах ML-задач — не классификация с фиксированным числом классов,
а генерация структурированного описания видео с временной привязкой (grounding).

Формально: `видео → [{start, end, action, object, keyframe, confidence}]`,
время в секундах, `start ≤ keyframe ≤ end`.

### 2.2. Блок-схема решения

Архитектура сервиса и последовательность обработки — [project-overview.md §4.1](project-overview.md),
[architecture.md](architecture.md), [diagrams.md](diagrams.md).

**Бейзлайн** (реализован, остаётся в реестре как инструмент отладки): синтетические
пайплайны `overlap`, `dense`, `sequential` — корректная структура ответа, синтетическое
содержание. Позволяют прогонять цикл без расхода запросов к API.

**Исследовательский бейзлайн ветки A:** самоподобие эмбеддингов скользящим окном
(VideoMAE / TimeSformer / ViViT / DINOv2 / CLIP) + поиск границ (`adjacent`, TW-FINCH).
Даёт только интервалы, без названий. В MVP не вошёл — см. project-overview §4.3.

**MVP:** video-VLM за один проход, две независимые ветки:

| Пайплайн | Модель | Где выполняется | Статус |
|---|---|---|---|
| `pegasus_analyze` | TwelveLabs Pegasus 1.5 | Внешний API | Работает в проде |
| `pegasus_segment` | TwelveLabs Pegasus 1.5 | Внешний API | Работает в проде |

**Режим по умолчанию — `pegasus_analyze`.** По результатам прогонов на реальных роликах
он выдаёт атомарные шаги с конкретным действием; `pegasus_segment` формулирует действия
обобщённо и хуже дробит ролик на атомарные шаги. Оценка качественная, на эталоне
разница пока не измерена (project-overview §5.3).
| `marlin2b` | Marlin-2B (Apache 2.0) | Локально, через `llama.cpp` | Готовится, отдельная ветка |

### 2.3. Этапы решения задачи

#### Данные и сущности

Обучения нет — модели используются как есть. Данные нужны **только для оценки**.

| Источник | Что даёт | Объём | Статус |
|---|---|---|---|
| EPIC-KITCHENS (клипы + перенос аннотаций на них) | Быстрый ground truth в домене кухни | 3 клипа из одной записи | Клипы есть, перенос аннотаций не сделан |
| Собственная съёмка вне домена кухни | Проверка обобщаемости на скрытый набор кейса | План 20–50 роликов | Не снято |
| Скрытый набор кейсодателя | Финальная оценка | 8–12 роликов | Недоступен до защиты |
| Пользовательские правки в проде (`annotations.status = EDITED`) | Косвенный сигнал качества: что именно правит человек | Накапливается | Не анализируется |

Персональные данные: на роликах присутствуют люди — см. §4.5.

#### Формирование выборок

Обучающей выборки нет. Выборки две:

- **Разработческая** (3 клипа EPIC-KITCHENS) — на ней подбирались параметры ветки A
  и проверялась работоспособность промптов. Выводы, полученные на ней, **нельзя**
  переносить на общий случай: это три клипа одной записи одной кухни.
- **Оценочная** — эталон, размеченный вручную и не участвовавший в разработке.
  Не собран; это блокер всех метрик качества и первый пункт плана работ.

Разделение по записям, а не по клипам: клипы из одной записи слишком похожи, и
смешение дало бы завышенную оценку.

#### Целевая переменная и метрики

Целевая переменная — эталонная разметка: список интервалов с действием и объектом.

| Метрика | Что меряет | Порог | Приоритет |
|---|---|---|---|
| Step-level F1 | Совпадение множества шагов с эталоном | ≥ 0,75 | Главный |
| Точность пары «действие + объект» | Качество классификации | ≥ 80 % | **Главный (требование заказчика)** |
| Средняя абсолютная ошибка границ | Точность сегментации | ≤ 2 с | Порог, не цель |
| Доля валидных экспортов | Надёжность контракта | 100 % | Достигнуто |

Продуктовые метрики (доля принятых без правок, доля переразмеченных заново и др.) —
`product/04`, уровень 2.

#### Риски этапа и минимизация

Полный реестр рисков и план проверки допущений — `product/05`. Специфичные для ML:

| Риск | Минимизация |
|---|---|
| Нет эталона → метрики неизвестны | Два пути параллельно: перенос аннотаций EPIC и своя разметка |
| Выводы получены на 3 клипах одной кухни | Съёмка роликов вне домена до финала |
| Модель ломает формат ответа | Статусы `OK` / `SCHEMA_ERROR` / `INVALID_JSON`, сырой ответ сохраняется, `AnnotationSegment` чинит границы |
| Черновик хуже пустого экрана | Метрика-предохранитель P2; `confidence` в контракте; кнопка полной очистки разметки |
| Внешний API меняет версию модели → результаты не воспроизводятся | `model_version` хранится вместе с результатом; альтернативная ветка на открытых весах |

#### Бизнес-проверка результата

Численные метрики недостаточны: они не отвечают на вопрос, стало ли быстрее.
Финальная проверка — замер на людях по протоколу из `product/04`: те же ролики,
два режима (с нуля / правка черновика), разнос по времени, обязательная сверка
с эталоном, чтобы не выдать небрежность за ускорение.

## 3. Подготовка пилота

### 3.1. Способ оценки пилота

Дизайн — `product/04`, «Протокол замера ускорения»: 10 роликов, не участвовавших
в разработке, минимум 2 участника, перекрёстные наборы, разнос между режимами не
менее суток. Замеряем время до готовой разметки, число действий мышью и клавиатурой,
субъективную усталость; контролируем качество сверкой с эталоном.

### 3.2. Успешный пилот

- Время на ролик сократилось ≥ 3× **без** просадки качества относительно эталона;
- доля сегментов, принятых без правок, ≥ 60 %;
- доля роликов, размеченных заново с нуля, ≤ 5 % (метрика-предохранитель);
- доля роликов, обработанных без ошибки пайплайна, ≥ 95 %.

### 3.3. Вычислительные затраты

| Конфигурация | Требования | Время на ролик 30 с |
|---|---|---|
| Синтетические пайплайны | CPU, доли секунды | < 1 с |
| `pegasus_*` (внешний API) | GPU не нужен; нужен интернет и ключ API | Минуты; ограничение BR7 (≤ 2 мин) выдерживается |
| `marlin2b` (локально) | Запуск через `llama.cpp` — без стека torch/torchcodec; **5 486 МиБ VRAM** по замеру на `llama-server`, достаточно карты 8 ГБ; 2B параметров, сэмплирование 2 FPS, до 240 кадров | Время на ролик не замерено |

Инфраструктура: 6 контейнеров (frontend, backend, ml-service, postgres, redis, minio),
разворачивается на одной машине. Хранилище: исходное видео + `annotation.json` на ролик.

## 4. Внедрение

### 4.1. Архитектура решения

[project-overview.md §4.1](project-overview.md) и [architecture.md](architecture.md).
Кратко: браузер → FastAPI (состояние, PostgreSQL) → Redis Stream (очередь) →
ml-service (консьюмер, инференс) → S3 (видео и артефакты) → колбэк в бэкенд.

Инварианты, на которых держится дизайн (полностью — в `AGENTS.md`):
бэкенд владеет бизнес-состоянием, Redis только транспортирует задачи;
байты видео никогда не проходят через бэкенд и Redis; модельная специфика заперта
в `ml-service`; контракт разметки заморожен; один ролик = одна задача.

### 4.2. Инфраструктура

Docker Compose, без внешних управляемых сервисов. Сознательный отказ от
Kafka/RabbitMQ/Celery и отдельного воркер-сервиса: Redis Streams с consumer-группой
даёт нужную гарантию доставки (`XACK`, задача не теряется при перезапуске),
всё остальное — оверинжиниринг для этого объёма.

**Масштабирование.** Точка роста — число реплик `ml-service` в одной consumer-группе:
задачи распределяются между консьюмерами без изменения кода. Ограничение —
внешний API (rate limit) или число GPU для локальной ветки.

### 4.3. Требования к работе

| Показатель | Текущее значение | Комментарий |
|---|---|---|
| Время обработки ролика | ≤ 2 мин (BR7 выдерживается на Pegasus) | Измеряется от `QUEUED` до `COMPLETED` |
| Пропускная способность | **1 ролик одновременно** | Консьюмер читает поток с `count=1`; следующая задача ждёт в `QUEUED`. При пакетной загрузке 100 роликов последний ждёт часы |
| Доступность | Не гарантируется | Хакатонная конфигурация: один экземпляр каждого сервиса, без резервирования |
| Потеря задач | Не происходит | Consumer-группа с `XACK`; упавшая задача переводится в `FAILED` с трейсбеком, сообщение подтверждается |
| Деградация при недоступности внешнего API | Задача падает в `FAILED` с явным сообщением | Пользовательские данные не теряются; повторный запуск возможен |

**Вывод для промышленного применения:** узкое место — последовательная обработка.
Пакетный сценарий (сотни роликов) требует горизонтального масштабирования консьюмеров;
архитектурно это готово, эксплуатационно — не проверено.

### 4.4. Безопасность системы

Полностью — [project-overview.md §4.4](project-overview.md). Кратко: bcrypt + JWT
(HS256, 7 дней), доступ к чужим объектам отдаёт 404, а не 403; служебные маршруты
`/api/internal/...` закрыты общим секретом; файлы доступны только по presigned-URL
с ограниченным сроком; БД, Redis и MinIO не выведены наружу; CORS по белому списку.

Известные уязвимости хакатонной конфигурации: небезопасные значения секретов
по умолчанию, отсутствие TLS, невозможность отозвать выданный JWT, отсутствие
аудита изменений разметки. Все три — блокеры промышленного внедрения, ни один
не является архитектурным.

### 4.5. Безопасность данных

**Обрабатываемые данные — персональные.** На роликах человек: лицо, руки, рабочее
место; в ряде юрисдикций видеозапись человека относится к биометрическим данным.
Пользовательские данные системы ограничены логином и хешем пароля.

| Аспект | Состояние |
|---|---|
| Хранение видео | В S3 заказчика (MinIO в компоуз-конфигурации), бакет закрыт, доступ только по подписанным ссылкам |
| **Передача третьей стороне** | **Да, в пайплайнах `pegasus_*`:** ролик выгружается во внешний API TwelveLabs, то есть покидает контур заказчика |
| Альтернатива без выгрузки | Ветка `marlin2b`: открытые веса, локальный инференс, видео не покидает периметр |
| Срок хранения и удаление по требованию | Не реализованы: удаление видео есть, политики хранения и каскадного удаления производных артефактов нет |
| Обезличивание | Не реализовано и в рамках задачи невозможно: действие человека — это и есть предмет разметки |
| Журналирование доступа к видео | Отсутствует |

**Требование к внедрению.** Заказчик обязан выбрать конфигурацию осознанно: внешний
API даёт качество без GPU ценой выгрузки персональных данных наружу; локальная ветка
исключает выгрузку ценой требований к железу. Реестр пайплайнов сделан именно для
того, чтобы это был параметр развёртывания, а не архитектурное решение. При работе
с персональными данными требуется согласие снятых людей и договор с провайдером —
это вне нашей компетенции, но должно быть названо явно.

### 4.6. Издержки

Полный расчёт — [project-overview.md §6.4](project-overview.md). Сводка на ролик
30 секунд, курс 80 ₽/$:

| Статья | Значение | Достоверность |
|---|---|---|
| Инференс `pegasus_*` | ≈ $0,039 · **3,1 ₽** за ролик (индексация $2,50/ч + Analyze $1,75/ч видео + $7,50 за 1 млн выходных токенов) | Расчёт по прайсу Developer; **счётом не подтверждено** — прогоны укладываются в free-лимит 600 мин/мес |
| То же на объём | ≈ 3 100 ₽ за 1000 роликов; ≈ 375 ₽ за час видео; ≈ 0,4–0,6 ₽ за размеченный сегмент | Производная от строки выше |
| Инференс `marlin2b` | 0 ₽ переменных расходов. Замер: **5 486 МиБ VRAM** на `llama-server` — достаточно карты 8 ГБ | Снято с работающего процесса |
| Точка перехода на локальную ветку | ≈ 9,5 тыс. роликов при цене карты ~30 тыс. ₽ | Расчёт |
| Инфраструктура | Одна машина под 6 контейнеров + хранилище видео | Порядок величины понятен |
| **Экономия для заказчика** | ≈ 733 тыс. ₽ на 1000 роликов при ускорении 3× | Расчёт — `product/02` |

Ключевое: стоимость обработки — **0,3 % от стоимости ручной разметки** того же ролика,
то есть экономика продукта от неё не зависит и определяется только реальным ускорением
работы человека. Кейс всё же требует фактического счёта, а не расчёта по прайсу —
это открытый пункт. Выбор `marlin2b` статью обнуляет, превращая переменные расходы
в разовую покупку карты.

### 4.7. Integration points

| Взаимодействие | Протокол | Аутентификация |
|---|---|---|
| Браузер → backend | REST `/api/...` | JWT (Bearer) |
| Браузер → S3 | PUT/GET по presigned-URL | Подпись в URL, срок 1 час |
| Backend → Redis | `XADD` в поток `ml-jobs` | Внутренняя сеть |
| ml-service → Redis | Consumer-группа, `XREADGROUP` / `XACK` | Внутренняя сеть |
| ml-service → S3 | Скачивание видео, загрузка `annotation.json` | Ключи доступа |
| ml-service → PostgreSQL | Чтение словарей проекта | Внутренняя сеть |
| ml-service → backend | Колбэки статуса `/api/internal/...` | `INTERNAL_API_TOKEN` |
| ml-service → TwelveLabs | HTTPS, SDK | `TWELVELABS_API_KEY` |

Внешняя зависимость ровно одна — TwelveLabs, и она изолирована внутри одного пайплайна.

### 4.8. Риски

Полный реестр — `product/05` (продуктовые, технические, организационные, с оценкой
вероятности и влияния). Главные на текущий момент:

1. **Нет эталона** — качество не измерено, ни одно утверждение о F1 и границах
   не подкреплено числом. Первый пункт плана работ.
2. **Черновик хуже пустого экрана** — если модель систематически ошибается, продукт
   приносит отрицательную пользу. Отслеживается метрикой P2.
3. **Обобщаемость** — все экспериментальные выводы получены на трёх клипах одной кухни.
4. **Внешний API как точка отказа и как канал утечки ПДн** — снимается веткой
   `marlin2b`, но её качество на нашей задаче ещё не измерено.
5. **Последовательная обработка** — пакетный сценарий заказчика упирается
   в пропускную способность одного консьюмера (§4.3).
